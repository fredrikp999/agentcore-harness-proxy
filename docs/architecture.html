Agent Proxy Architecture

A browser, a script or an MCP client reaches the AgentCore harness in eu-west-1 through Cloudflare Access, an edge Worker and a streaming Lambda. The Lambda holds the only AWS permission, so callers never hold AWS keys.

In more detail

How the pieces fit together

What each client does, what happens to one chat message from start to finish, what the agent can reach, and which part of the repository deploys which box.

Three ways in

cloudflare/web · browser

Web chat UI

You open https://<your-hostname>/ and sign in through an Access Allow policy, for example email with a one-time PIN. Access sets a CF_Authorization cookie and, on every request, adds the signed JWT as the Cf-Access-Jwt-Assertion header.

The page loads the harness list from GET /api/harnesses and sends each message to POST /api/chat. Each chat is one harness session; its id (web-<uuid>) is the session id. Chats live only in the browser's local storage.

clients/invoke_proxy.py · curl

Scripts and curl

The caller sends a service token as CF-Access-Client-Id and CF-Access-Client-Secret. Access accepts it only through a separate Service Auth policy, and then adds the same kind of JWT header.

The request body is JSON (message, optional session_id, harness, max_tokens). The reply streams as plain text; the session id comes back in x-session-id, so the next call can continue the conversation.

/api/mcp · Claude Code, clients/mcp_proxy.py

MCP clients

An MCP client sends the same service token headers, added for example with claude mcp add --transport http ... --header. The endpoint is stateless Streamable HTTP with one tool, ask_agent, which takes the same four fields.

The tool returns the whole reply and its session_id at once. While the agent works, the SSE response carries a comment every 15 seconds so nothing on the way times out. claude.ai and Claude Desktop connectors need OAuth, which isn't set up.

Either way, the identity the Lambda sees is the first non-empty of the JWT's email (a person), common_name (a service token) or sub. A service token's sub is an empty string, which is why the order matters.

One chat message, step by step

  1. Access. Cloudflare checks the cookie or the service token against the application's policies. Without a match the browser is sent to the login page and a script gets 403; nothing reaches AWS.
  2. Worker. /api/* runs the Worker's code first. It removes the service token headers and the browser cookie (the JWT header already carries the identity) and calls the Lambda function URL with fetch(), which sets the Host header the function URL requires. Any other path is answered from the static UI files.
  3. JWT check. The Lambda verifies Cf-Access-Jwt-Assertion against the team's public keys at https://<team>.cloudflareaccess.com/cdn-cgi/access/certs, checking the signature, the issuer and the application's AUD tag. This is the real lock: the function URL itself is public.
  4. Validation. The body must be JSON with a 1 to 20,000 character message. session_id must be at least 33 characters of A-Za-z0-9_- (a new one is generated if absent). max_tokens defaults to 1000 and is capped at 8000. harness is a name that the Lambda maps to an ARN; callers never see or send ARNs.
  5. InvokeHarness. The Lambda calls the harness with its own role, passing only the message, session id and token limit. Callers cannot override the model, prompt, tools or skills, even though the API would allow it.
  6. The agent loop. AgentCore starts or resumes the session's microVM and runs the loop: the model reasons, calls tools (Code Interpreter, the MCP servers, the built-in shell and file tools), reads the results and repeats, up to 75 iterations or 1 hour.
  7. Streaming back. The Lambda writes each text delta to the response as it arrives (text/plain, function URL in response-streaming mode). If the harness fails mid-reply, the stream ends with [error: ...], which the UI shows as an error. For /api/mcp the Lambda collects the text instead and sends it as one JSON-RPC result.

The MCP server

Other agents can use this agent as a tool. POST /api/mcp is a stateless Streamable HTTP MCP server in the same Lambda as the chat API, behind the same Access application, with one tool.

AspectWhat it is
Toolask_agent: sends a message to the agent and returns its full reply.
Inputsmessage (required, up to 20,000 characters), session_id, harness (an enum of the configured names), max_tokens (up to 8000). The same checks as /api/chat. Plus include_trace, see below.
OutputstructuredContent {reply, session_id}, and the same JSON as a text block for clients that only read text. Errors come back as a result with isError.
TraceWith include_trace: true, a trace list too: the agent's reasoning (its <thinking> blocks, or the model's own reasoning output), each tool call with its input, and each tool result, in order and each cut to 2,000 characters. Off by default, so callers don't pay for it in context. The reply never contains the reasoning.
ConversationEach call without session_id starts a new harness session. Passing it back continues that session, with the same 15-minute idle limit as the chat.
TransportOne JSON-RPC message per POST, no Mcp-Session-Id. tools/call answers over SSE with keepalive comments; other methods answer with JSON. GET and DELETE return 405.
AuthA service token in CF-Access-Client-Id and CF-Access-Client-Secret. A request with an Origin header gets 403.
Not yetclaude.ai and Claude Desktop connectors, which need OAuth instead of fixed headers. Token-by-token streaming of the reply.

To add it to Claude Code: claude mcp add --transport http agent https://<your-hostname>/api/mcp --header "CF-Access-Client-Id: <id>.access" --header "CF-Access-Client-Secret: <secret>". To try it from a terminal: uv run clients/mcp_proxy.py --list, then uv run clients/mcp_proxy.py "Hello".

Sessions and state

  • A session is identified by the id the client sends. The harness keeps the conversation inside that session's microVM, trimmed to the last 150 messages.
  • A session ends after 15 minutes idle or 8 hours in total. After that the same id starts afresh and the agent no longer remembers earlier messages; the web UI warns when you return to such a chat.
  • There is no long-term memory yet (AgentCore Memory is disabled), so nothing carries over between sessions.
  • The web UI stores chat history in the browser only. The proxy and the Lambda store nothing; the Lambda logs errors to CloudWatch, kept for one month.

Security boundaries

  • No AWS keys outside AWS. Only the Lambda's role can call InvokeHarness and InvokeAgentRuntime, and only on the configured harness ARNs.
  • Two checks of one identity. Access decides who may enter; the Lambda verifies Access's signature, so a request that bypasses Cloudflare and hits the public function URL gets 401.
  • No browser calls to MCP. /api/mcp refuses requests with an Origin header, so a web page can't use a signed-in visitor's Access cookie to call the agent as a tool.
  • Secrets stop at the edge. The Worker drops the service token headers and the browser cookie before calling AWS.
  • A narrow request shape. The Lambda forwards four fields. Tool, model and skill overrides from callers never reach the harness.
  • Least-privilege harness role. The execution role covers the configured model and, per enabled tool, only that tool's actions on the AWS-managed resource.
  • Values that describe your setup stay local. Hostname, Access AUD, account id and tokens live in git-ignored files: .env, aws/deploy.local.json, cloudflare/worker/wrangler.jsonc.
